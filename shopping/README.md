# עגלה לשניים 🛒❤️

עדכון מואני וסיום קנייה: [הוראות הפעלה, קבלה בדיעבד ועדכון קיצור הדרך](MOANI_AND_COMPLETION.md). בפרויקט קיים יש להריץ גם את `supabase/migrations/202611110001_finish_without_receipt.sql` כדי לאפשר סיום ללא קבלה בענן.

אפליקציית קניות נפרדת בעברית ו־RTL, בתוך `shopping/`. אפליקציית Fitness בשורש המאגר נשארת ללא שינוי בקוד ובנתונים שלה.

## מה פועל ללא שירות חיצוני

- רשימות עם שם, לוח שנה ותאריך (ברירת מחדל: חמישי הקרוב, כולל היום אם חמישי).
- יותר מ־200 מוצרים נפוצים בישראל, חיפוש חלקי, קטגוריות, מוצרים אישיים, כמויות ויחידות.
- סימון וביטול איסוף, עריכה ומחיקה, פס התקדמות ושכפול ללא סימונים.
- שמירה בדפדפן; תמונות קבלות ב־IndexedDB. קבלות ידניות עם התאמה למוצר ובדיקת כל שורה לפני אישור.
- מחיר בפועל ליחידה לאחר הנחות; השוואה רק בין אותו מוצר ואותה יחידה. אין המרה שקטה בין אריזות/משקל/יחידות.
- הוצאות חודשיות, היסטוריה ותדירות לפי קבלות מאושרות. גיבוי ושחזור JSON; תמונות אינן כלולות בגיבוי.
- PWA עם מעטפת סטטית שנפתחת שוב ללא רשת לאחר טעינה ראשונה מוצלחת. הנתונים האישיים אינם נשמרים במטמון service worker.
- איור זוגי שנוצר על בסיס האיורים שסיפק המשתמש ב־`public/couple-shopping.png`, וניתן להחלפה.

**עדכון סנכרון:** בפרויקט Supabase קיים חובה להריץ גם את `202611080001_cloud_sync.sql`. ראו [הוראות התיקון והייבוא הבטוח](supabase/CLOUD_SYNC_FIX.md). כאשר משתני Supabase מוגדרים, כתיבה מחייבת התחברות, חברות בבית וטעינה מוצלחת; אין fallback מקומי.

**מצב מקומי אינו משותף בין טלפונים ואינו גיבוי ענן.** מחיקת נתוני הדפדפן עלולה למחוק רשימות ותמונות. שיתוף ואימות זהות זמינים בקוד רק לאחר הגדרת Supabase; OCR אינו פועל ללא שירות מוגדר. הממשק מציין זאת במפורש.

## פיתוח ובדיקות

נדרשים Node.js 24, npm ו־Python 3 (להגשת הייצוא הסטטי). לבדיקות דפדפן נדרש Chromium. בסביבה זו הוא מותקן ב־`/usr/bin/chromium`; אפשר להגדיר `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` במערכת אחרת.

```sh
cd /workspace/Itzik/shopping
npm ci
npm run dev
```

```sh
npm run typecheck
npm test
npm run build
npm run test:e2e
```

להגשת הבנייה: `npm start` (פורט 3000). `next start` אינו מתאים לייצוא סטטי. הבנייה עצמאית; אין צורך להפעיל את Expo. הגדרת `experimental.useTypeScriptCli: false` משתמשת ב־API המהדר הרגיל עקב כשל parsing בנתיב CLI של Next 16.4 בסביבה הזאת; בדיקת TypeScript מלאה עדיין רצה בבנייה ובפקודה נפרדת.

## פרסום ללא Vercel

GitHub Pages יכול להגיש את שני האתרים בנפרד באותו מאגר:

- Fitness נשאר ב־`/Itzik/`.
- האפליקציה הזאת ב־`/Itzik/shopping/`.

ה־workflow הקיים בונה את Fitness כרגיל, ואז בונה את `shopping` עם `NEXT_PUBLIC_BASE_PATH` המתאים ומעתיק את `shopping/out/` לתוך `dist/shopping/`. מחולל ה־service worker של Fitness רץ **לפני** העתקת האפליקציה החדשה, ולכן לא מוסיף אותה לרשימת precache של Fitness. המטמון של הקניות משתמש בקידומת ייעודית ואינו מוחק מטמונים של Fitness. אין להעביר תמונות קבלות או נתוני משתמש לתיקיות `public/`, `out/` או ל־Git.

```sh
NEXT_PUBLIC_BASE_PATH=/Itzik/shopping npm run build
```

הכתובת לעיל היא כתובת יעד, לא הוכחת פרסום. יש לאמת HTTP ותפקוד לאחר פריסת Actions מוצלחת. על מארח מותאם מומלץ להגדיר `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` ו־HTTPS; GitHub Pages אינו מאפשר כותרות שרת מותאמות.

ב־Vercel ניתן להגדיר Root Directory ל־`shopping`, פקודת build ל־`npm run build`, Output Directory ל־`out`. אין צורך ב־Vercel לשימוש המקומי או ל־Pages.

## ענן אופציונלי: Supabase

התשתית נכתבה אך אינה נחשבת מאומתת מול Supabase עד בדיקה בפרויקט אמיתי. אין צורך בה כדי להשתמש בגרסה המקומית.

1. יוצרים פרויקט, מפעילים לפי הסדר את `supabase/migrations/202611050001_shopping.sql` ואת `supabase/migrations/202611080001_cloud_sync.sql`, ומאפשרים הרשמת דוא״ל וסיסמה עם אישור דוא״ל.
2. מגדירים את Site URL ו־Redirect URLs לכתובת האתר (כולל נתיב הקניות), ומגדירים SMTP אמיתי לפני שימוש קבוע.
3. בזמן הבנייה בלבד מגדירים `NEXT_PUBLIC_SUPABASE_URL` ו־`NEXT_PUBLIC_SUPABASE_ANON_KEY` (מפתח publishable/anon, לעולם לא service role).
4. כל אחד יוצר חשבון אישי. הראשון יוצר בית וקוד הזמנה, והשני מצטרף. הקוד חד־פעמי, אקראי, מגובב, תקף 24 שעות; הבית מוגבל לשני משתמשים.
5. בודקים בשני דפדפנים הוספה וסימון בזמן אמת; בניתוק אין אישור שמירה. מחיקה נבדקת גם ברענון תקופתי כגיבוי משום שאירועי DELETE מסוננים אינם מובטחים ב־Realtime.
6. יוצרים משתמש שלישי ובית שני ובודקים שלא ניתן לקרוא או לשנות רשימות/פריטים/קבלות/תמונות של הבית הראשון, גם דרך REST/RPC ישירים. בודקים שעדכון עם גרסה ישנה נדחה ושקבלה מאושרת לא נדרסת.

כל הטבלאות מוגנות ב־RLS, כתיבות נעשות ב־RPC שמוודא שיוך לבית. לפריטים ולרשימות יש גרסאות למניעת דריסת עריכות; לאישור קבלות יש נעילה טרנזקציונית. התמונות נשמרות ב־bucket פרטי. אין שימוש במפתח service role בדפדפן או בפונקציית הזיהוי. נתונים מקומיים אינם עוברים אוטומטית לענן.

### זיהוי קבלות אופציונלי

פונקציית `supabase/functions/recognize-receipt/index.ts` נפרסת ל־Supabase Edge Functions לאחר יצירת הפרויקט. שומרים שם בלבד `RECEIPT_AI_API_KEY`, ובמידת הצורך `RECEIPT_AI_MODEL` (ברירת המחדל `gpt-4.1-mini`). מגדירים `SHOPPING_ALLOWED_ORIGINS` לרשימת origins מדויקים, לדוגמה `https://izick8-hub.github.io` (ללא נתיב). מפתחות אינם נכללים בקובצי האתר או ב־Git.

הפונקציה מאמתת משתמש, קוראת תמונה תחת הרשאותיו, מגבילה גודל וקצב שימוש (3 לדקה, 30 ליממה לבית), ושולחת אותה ל־OpenAI. **תמונה נשלחת לספק AI חיצוני רק לאחר לחיצה על פענוח.** הפלט מובנה ונבדק עם Zod; אינו מעדכן את בסיס הנתונים ואינו מאשר מחירים. כל שורה נדרשת לבדיקה ידנית. אם שירות לא זמין, נותרת הזנה ידנית. גישה לענן, ספק AI, תמחור ודיוק OCR בעברית טרם אומתו בסביבה זו.

## מקור הקטלוג

הקטלוג ב־`lib/catalog.ts` הוא קטלוג התחלתי עצמאי של שמות מוצרי סופר נפוצים — **לא מאגר רשמי של יוחננוף וללא מחירים מומצאים**. ניסיון גישה לאתר הרשת נחסם במדיניות הרשת של הסביבה (403), ולא אומת מקור רשמי נגיש או רישיון ייבוא. לכן לא בוצע scraping ולא יובאו נתוני רשת. שדה `source`, מזהה מוצר יציב וקטגוריות מאפשרים להוסיף מקור מורשה בעתיד; יש לבדוק רישוי, מזהי ברקוד, אריזה, סניף ותאריך עדכון לפני יבוא.

## מגבלות בדיקה

בדיקות Chromium אינן בדיקת Safari או התקנה בפועל באייפון. האפליקציה אינה מספקת סנכרון ללא backend. בקבלות נדרשת כרגע התאמה ידנית; פלט AI (כשמוגדר) מסומן כולו כלא מאושר. שמירת מחירים אינה מוחקת רשומות קודמות. קבלה מאושרת ניתנת לצפייה בלבד; זיכויים שליליים וקבלות החזרה אינם נתמכים בגרסה הראשונה.
