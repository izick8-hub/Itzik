# תיקון סנכרון — הוראות לפרויקט Supabase הקיים

## מה נמצא ותוקן בקוד

בגרסה הישנה הוגדר מצב `local` כברירת מחדל, ו־`ready` הופעל לפני סיום שחזור ההתחברות ובירור הבית. שגיאת שחזור התחברות לא נבדקה, וכשל בבירור החברות לא חסם כתיבה מקומית. כך היה אפשר לשמור בהצלחה במכשיר בזמן שהחיבור טרם הוכרע, או אחרי יציאה/אובדן התחברות. בנוסף, listener לאחסון מקומי החליף את נתוני המסך גם במצב ענן. רענון טוקן איפס את הבית גם כשזהות המשתמש לא השתנתה. אלו כשלים מוכחים בקוד; אין בסביבה גישה לפרויקט הייצור כדי לקבוע איזו שרשרת אירועים התרחשה אצל המשתמשים.

כעת, כאשר Supabase מוגדר, אין נפילה אוטומטית לכתיבה מקומית — גם לא כשלא מחוברים או כשיש שגיאה. רק לאחר התחברות, חברות בבית וטעינת snapshot מוצלחת מתאפשרת שמירה. נתוני localStorage נשמרים בנפרד ולא מוצגים כאילו נטענו מהענן. אירועי אחסון ישנים אינם דורסים את תצוגת הענן.

`shopping_commit` קושר את הפעולה לבית שנטען, מפעיל את `shopping_mutate` הקיים, וקורא את הנתונים בחזרה בתוך אותה עסקת PostgreSQL. הלקוח מאמת את הבית ואת הרשומה לפני הודעת הצלחה. שגיאות קריאה/שמירה מוצגות עם קוד בטוח, בלי מפתחות או תוכן שגיאת שרת גולמי. אם התשובה אובדת אחרי commit, מוצגת אי־ודאות — אין הבטחת כישלון או הצלחה שאין לה בסיס. מזהי יצירת רשימה/מוצר נשארים יציבים בניסיון חוזר באותו טופס.

## פעולה הכרחית — הרצת migration נוסף

**לא הונח שהקובץ כבר הורץ. הוא לא הורץ בפרויקט הייצור על ידי הסוכן.**

1. פתחו את **הפרויקט הקיים** ב־Supabase Dashboard → **SQL Editor** → **New query**.
2. העתיקו את כל התוכן של `shopping/supabase/migrations/202611080001_cloud_sync.sql` מה־commit העדכני ב־GitHub, והפעילו **Run**.
3. יש להריץ את הקובץ במלואו, כולל `begin` ו־`commit`. הוא נוסף על קובץ ההקמה הקודם, לא מחליף אותו. **אין להריץ מחדש את קובץ ההקמה מ־5 בנובמבר, למחוק טבלאות או לשחזר את הפרויקט.**
4. הקובץ מוסיף שלוש פונקציות ציבוריות, טבלת סימון ייבוא וטריגר מחיקה. הוא אינו מוחק נתונים, אינו משנה את בית המשתמשים, ואפשר להריץ אותו שוב. הוא משאיר INSERT/UPDATE/DELETE ישירים חסומים; כתיבה מאושרת נעשית רק דרך RPC.
5. אפשר לוודא שהפונקציות קיימות באמצעות השאילתה הבאה (ללא מפתחות או נתונים אישיים):

```sql
select
  to_regprocedure('public.shopping_snapshot(uuid)') is not null as snapshot_ready,
  to_regprocedure('public.shopping_commit(jsonb,uuid)') is not null as commit_ready,
  to_regprocedure('public.shopping_import_local(jsonb,uuid)') is not null as import_ready;

select tablename
from pg_publication_tables
where pubname = 'supabase_realtime'
  and schemaname = 'public'
  and tablename in ('shopping_lists','shopping_items','shopping_products','shopping_receipts');
```

צפויים שלושה ערכי `true` וארבע טבלאות בפרסום Realtime. עד שה־migration זמין, הגרסה החדשה מציגה הודעה שחסרה הגדרת בסיס הנתונים וחוסמת שמירה; היא לא מייצרת נתונים מקומיים בשקט.

## שמירת הרשימה שכבר הכנתם וייבוא בטוח

1. **אל תמחקו נתוני אתר, אל תנקו localStorage ואל תסירו את האפליקציה.** בצעו את הייבוא באותו דפדפן ובאותה כתובת שבה נוצרה הרשימה.
2. לאחר הרצת ה־migration ופרסום הגרסה, רעננו את האתר והתחברו לחשבון המקורי. בהגדרות צריך להופיע `בית משותף בענן` רק אחרי שהטעינה הצליחה.
3. פתחו **הגדרות ושיתוף**. באזור **הרשימות המקומיות שלכם נשמרו במכשיר**, לחצו קודם על **הורדת גיבוי מקומי לפני הייבוא**.
4. סמנו את הרשימות הרצויות ואת תיבת האישור **אני מאשר להעתיק את הרשימות שבחרתי לבית המשותף בענן**. לחצו **ייבוא הרשימות שבחרנו לענן**.
5. ההעברה מעתיקה שמות, תאריכים, מוצרים אישיים, כמויות, יחידות וסימוני איסוף, בלי למחוק את המקור המקומי. מזהי המקור נשמרים, ועסקה אחת מגינה מפני ייבוא חלקי. ייבוא חוזר לא יוצר כפילויות, לא דורס שינוי שכבר נעשה בענן ולא מחזיר מוצר שנמחק אחרי הייבוא.
6. קבלות ותמונות אינן מועברות במנגנון הזה. הן נשארות במכשיר. גיבוי JSON כולל את נתוני הקבלות המקומיות אבל לא את קובצי התמונות; אין המצאה של נתיבי תמונה בענן.

## בדיקה חיה אחרי ההרצה — עדיין נדרשת

- משתמש א׳ יוצר רשימה חדשה ומוצר, ומוודא שנשמרו ב־`shopping_lists` וב־`shopping_items` באותו household.
- משתמש ב׳, בחשבון אחר באותו household, רואה את הרשימה והמוצר ללא רענון, משנה כמות ומסמן איסוף. השינוי מופיע אצל א׳.
- א׳ מוחק את המוצר; ב׳ רואה את המחיקה. הטריגר החדש מייצר UPDATE ברשימת האב משום שאירועי DELETE מסוננים אינם אמינים ב־Supabase Realtime.
- נתקו רשת: לא אמורה להיות הודעת הצלחת שמירה. החזירו רשת ובדקו טעינה מחדש/חיבור מחדש.
- התחברות או רענון לא אמורים להציג נתונים מקומיים כנתוני ענן. שגיאה לא אמורה להפעיל fallback מקומי.

אין צורך לפתוח מדיניות INSERT ציבורית או להשתמש ב־service role. אין לשתף מפתחות בצ׳אט. הפעלת Email, אישור כתובת דוא״ל ו־Redirect URLs נשארים כפי שהוגדרו לחשבונות הקיימים.

## מה אומת באופן אוטומטי

- `npm test`: בדיקות ניהול החיבור וה־SDK, כולל שני לקוחות, חסימת כתיבה בזמן התחברות, כשל שמירה, snapshot חסר, רענון טוקן, חיבור מחדש וייבוא מפורש. בדיקות אלו משתמשות בשירות בדיקה מדומה ומסומנות כך.
- `npm run test:postgres`: מכולת PostgreSQL 17 אמיתית, עם שני ה־migrations המקוריים. נבדקים תפקידי משתמש שונים, RLS בפועל, RPC בפועל, שמירה וקריאה באותה עסקה, עדכון ע״י בן הזוג, חסימת בית זר, עריכה עם גרסה ישנה, כפילויות, rollback וטריגר המחיקה. `auth.uid()` ומעטפת Storage מסופקים כתשתית בדיקה; שרתי Supabase Auth/Realtime עצמם אינם רצים בבדיקה הזאת.
- `npm run test:e2e`: בדיקות הדפדפן של הגרסה המקומית.
- בדיקות UI של מצב ענן: בנייה עם URL ומפתח בדיקה פיקטיביים בלבד, ו־`playwright.cloud.config.ts`. ה־HTTP מדומה; נבדקים כשל שמירה גלוי, אישור ייבוא ושימור הנתונים המקומיים. הן אינן הוכחת חיבור לפרויקט אמיתי.

לא אומתו בסביבה זו: הנתונים/ההרשאות בפועל בפרויקט שלכם, JWT אמיתי של שני המשתמשים, ערוץ Realtime חי בשני טלפונים או תוצאת הפריסה הציבורית. PostgreSQL מקומי ובדיקות UI אינם תחליף לאימות החי שלעיל.
